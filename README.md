## Что умеет кабинет

| | |
|---|---|
| **Сквозной путь в одном окне** | Подбор продукта → заявка → согласия → проверка → решение → подписание → выдача. Почта, мессенджеры и SMS для прохождения сценария не нужны. |
| **Автозаполнение по ИНН** | Данные компании подтягиваются из ЕГРЮЛ и «Прозрачного бизнеса» (смоделировано), черновик сохраняется сам. |
| **Проверка шансов до подачи** | Та же модель, что у банка, но без запроса в БКИ (о просрочках спрашиваем клиента): уровень шансов, факторы, вердикт по каждому продукту и комфортная сумма. Баллы и пороги не раскрываются. Из подбора открывается окном поверх страницы. |
| **Методика с источниками** | Балльная карта откалибрована логистической регрессией (Gini 0,74 на синтетическом портфеле). Просрочки учитываются по сроку и сумме (590-П, порог EBA). Залог снижает ставку через LGD по Базелю III и поднимает лимит. Прибыль должна покрывать платежи с запасом 25% (DSCR 1,25), выручка и прибыль из анкеты сверяются с ФНС. |
| **Роли внутри компании** | Бухгалтер готовит и принимает предложение, договор подписывает руководитель с правом подписи. Коллег добавляет руководитель — по чужому ИНН доступа не получить. |
| **Статус меняется на глазах** | Заявка идёт по конвейеру в фоне, этапы обновляются через HTMX каждые 2 секунды без перезагрузки страницы. |
| **Понятные причины решения** | Отказ или встречное предложение объясняются простыми словами: что повлияло и что можно сделать. |
| **Кабинет аналитика** | Очередь серой зоны и карточка заявки с четырьмя решениями: одобрить, предложить иные условия, запросить данные у клиента, отказать. |
| **Администрирование без кода** | Продукты добавляются и меняются в интерфейсе, у карты скоринга есть версии с откатом. На пульте «Тестовые данные» можно поменять кредитную историю и сведения ФНС любой компании или завести новую. Все правки попадают в журнал. |
| **Регистрация и безопасность** | Клиент регистрируется сам и подключает компанию по ИНН; по чужому ИНН доступа не получить. Лимит попыток входа, строгий CSP, защита сессии от подделки, RBAC на уровне сервиса. |
| **Надёжность банковского уровня** | Outbox в той же транзакции, `SKIP LOCKED`, три попытки к ФНС, `Idempotency-Key`, конфликт версий при параллельных решениях. |
| **ИИ там, где без него хуже** | Подбор по описанию своими словами и черновик сообщения клиенту для аналитика. Модель с открытыми весами, ответы сверяются с текстом, без модели — правила и шаблоны. |
| **Ничего платного** | Внешние сервисы — локальные моки. LLM необязательна, с открытыми весами, решений не принимает. |

# Как это выглядит

Все кадры сняты автоматически на демо-данных версии 1.2.1 с включённой моделью: никакой подготовки экранов
вручную, это работающий прототип.

## Кабинет клиента

### Главная: что происходит и что сделать

<img src="docs/readme/home.webp" alt="Главная Анны: баннер «Банку нужны данные», заявки с этапами и статусами, компания из ЕГРЮЛ, кто работает с заявками" width="100%">

Заявки компании с этапами и понятными статусами. Если банк ждёт действия, сверху баннер с
кнопкой и сроком. Справа данные компании из ЕГРЮЛ (смоделировано) и кто ещё работает с заявками:
финдиректор готовит, генеральный директор подписывает.

### Подбор своими словами

<img src="docs/readme/podbor.gif" alt="Клиент пишет «Нужно 3 млн на закупку товара к сезону, отдам за полгода, есть грузовик в залог» — форма подбора заполняется сама, плашка «Поняли так», подобраны продукты" width="100%">

Клиент пишет задачу как думает. Сначала фразу разбирают **правила** (мгновенно), модель с открытыми
весами зовётся только для трудных случаев. Форма заполняется сама, плашка «Поняли так: …» показывает,
что поняли и кто: правила или модель. Справа самопроверка по частым причинам отказа, ниже три
подходящих продукта с причинами «почему подходит» и предупреждениями.

### Проверка шансов до подачи

<img src="docs/readme/check.webp" alt="Проверка шансов: «Шансы высокие», факторы с отметками, что улучшит шансы и вердикт по каждому продукту" width="100%">

Та же балльная карта, что у банка, но **без запроса в БКИ** и без записи в базу. Финансы подставлены из
прошлой заявки. Клиент видит уровень шансов, факторы, ежемесячный платёж и долю прибыли, которая уйдёт на
кредиты, вердикт по каждому продукту, но не баллы и пороги. Залог с видом и стоимостью снижает ставку и
поднимает доступную сумму. Если сумма не проходит, подсказка называет комфортную сумму и срок, на котором
проходит вся сумма. Из подбора проверка открывается окном поверх страницы — подбор и введённые параметры
остаются на месте.

### Очередь серой зоны

### Карточка заявки: всё на одном экране

<img src="docs/readme/card.webp" alt="Карточка заявки KR-2026-0002: данные, проверки и источники со сверкой выручки и рентабельности с ФНС, скоринг 52 с разбивкой по факторам, кредитная логика с покрытием платежей и подсказкой суммы, форма решения, журнал статусов" width="100%">

Данные заявки и её снимок с sha256, ответы ФНС и БКИ со сверкой выручки и рентабельности, **скоринг
с разбивкой по факторам** (64 + 12 − 24 = 52, вероятность дефолта ≈ 8,4%), правила продукта, из-за которых
заявка на разборе (покрытие платежей 0,81× при норме 1,25×), и **подсказка системы** «допустимо до
5,6 млн ₽ на 36 мес., ставка 21,3%» — её можно одним нажатием подставить в решение. Ставка раскладывается
на базовую и ожидаемые потери. Справа четыре решения, внизу журнал.

# Запуск

## Требования к окружению

- **Docker** с плагином **Compose v2** (команда `docker compose`). Проверено на Docker 29.9 и Compose 5.6.
- Свободный порт **8000**.
- Интернет при первой сборке: скачиваются образы `python:3.12.7-slim-bookworm`, `postgres:16.4-alpine` и зависимости из `requirements.lock`.
- **Только если включать LLM** (необязательно): ещё ~3 ГБ свободной оперативной памяти (на машине целиком лучше от 8 ГБ),
  ~4 ГБ на диске (образ Ollama и модель 2,5 ГБ) и время на первое скачивание. Видеокарта не нужна: на обычном
  процессоре модель отвечает за 5–10 секунд.

Python, PostgreSQL и прочее ставить не нужно, всё внутри контейнеров.

## Команды

```bash
docker compose up --build
```

Откройте **http://localhost:8000**. Swagger: **http://localhost:8000/api/docs**.

При первом запуске контейнер `app` применяет миграции и загружает демо-данные
(идемпотентно, повторный запуск ничего не дублирует).

С LLM — тот же запуск с одним флагом, подробнее — [Где используется LLM](#где-используется-llm):

```bash
docker compose --profile llm up --build
```

Модель скачивать вручную не нужно: контейнер `ollama` при старте сам скачивает её (первый раз ~2,5 ГБ) и
загружает в память. Сайт открывается сразу и, пока модель не готова, работает на правилах и шаблонах.

| Команда | Что делает |
|---|---|
| `docker compose up --build -d` | собрать и запустить в фоне |
| `docker compose ps` | состояние контейнеров и healthcheck |
| `docker compose logs -f app worker` | логи сайта и конвейера |
| `docker compose down` | остановить, данные сохраняются |
| `docker compose down -v` | остановить и стереть базу и правки тестовых данных: при следующем запуске демо-данные создадутся заново |

# Сценарии проверки (T1–T10)

Все сценарии автоматизированы в [`tests/test_scenarios.py`](tests/test_scenarios.py).
Вручную в интерфейсе — под `anna@demo.local`, компания переключается в шапке:

| № | Как воспроизвести | Ожидаемо |
|---|---|---|
| T1 | «Северный ветер» → Подбор → оборотный 1 000 000 ₽ на 12 мес. → финансы → согласия → отправить | Статус меняется на глазах, авто-одобрение → Анна принимает → подписывает Игорь (`igor@demo.local`, у Анны нет права подписи) → «Выдан» |
| T2 | «Молодой старт» (4 мес.) → Подбор | Подбор сразу помечает продукты «Не подходит: компания должна работать не меньше N мес.» и предлагает «Кредит на старт бизнеса». Через API заявка на оборотный кредит → отказ «Срок работы бизнеса» + кнопка «Оформить „Кредит на старт“» |
| T3 | «Долговой центр» → любая заявка | Отказ «Платёжная история» (действующая просрочка в БКИ) |
| T4 | Мария → KR-…-0002 → «На иных условиях» → «Подставить в решение» (5,6 млн ₽ на 36 мес., 21,3%) → Анна принимает | MANUAL_REVIEW → COUNTEROFFER → … → DISBURSED |
| T5 | Мария → «Запросить данные» (ОСВ по счёту 62) → «Сформулировать для клиента»; Анна загружает `docs/samples/osv62_rashozhdenie.xlsx`; Мария видит «Распознано: … расхождение 17 %» и решает | MANUAL_REVIEW → NEEDS_INFO → MANUAL_REVIEW → APPROVED |
| T6 | Отказаться от предложения или дождаться истечения | OFFER_REJECTED или EXPIRED (истечение проверяет воркер) |
| T7 | Не отмечать согласие на БКИ | Кнопка отправки неактивна, API отвечает 422, запроса в БКИ нет |
| T8 | «Сбой связи» → любая заявка | Три попытки к ФНС, затем ручной разбор с пометкой «ФНС не ответил» |
| T9 | Двойная отправка; два аналитика решают одну заявку | Один результат; второй аналитик получает конфликт версии |
| T10 | Под `elena@demo.local` открыть `/applications/1`; на странице «Компания» ввести ИНН «Северного ветра» 7701234560 | 404; «Компания уже подключена к кабинету. Доступ выдаёт руководитель» |

Ещё:

- **«Закат»** (ликвидация) — отказ по жёсткому стопу.
- **Проверка шансов до подачи** (`/check`, кнопка на главной) — та же модель, что в конвейере, но без запроса в БКИ и без записи в базу. Клиент видит уровень шансов, факторы и вердикт по каждому продукту, но не баллы и пороги. Попробуйте «Северный ветер»: 2 млн на 24 мес. — шансы высокие; та же сумма на 6 мес. — шансы средние: прибыль не покрывает платежи с запасом, подсказка называет комфортную сумму (до 1,2 млн ₽) и срок, на котором проходят все 2 млн; 25 млн — шансы низкие. В подборе кнопка «Оценить шансы с этой суммой» открывает ту же проверку окном поверх страницы.
- **Новый клиент с нуля:** на странице входа «Зарегистрироваться» (ФИО, email, пароль, согласие на обработку ПД) →
  «Компания» → ИНН `7713550120` (синтетическая ООО «Новый горизонт», ни к кому не привязана) — данные подставятся
  из ЕГРЮЛ, вы станете администратором компании с правом подписи → подбор → заявка → решение → сами подписываете.
  Коллега регистрируется сам, а вы добавляете его по email в блоке «Команда» (с правом подписи или без);
  там же можно убрать сотрудника или выйти самому. Чужую компанию по ИНН подключить нельзя — доступ выдаёт её руководитель.
- **Профиль** (иконка с инициалами в шапке): данные и смена пароля. Восстановления по почте нет — по условию кейса
  сценарий не уходит в почту и SMS.

# Где используется LLM

ИИ помогает людям там, где без него хуже, и **не принимает кредитных решений**. Модель — Qwen3-4B-Instruct-2507
(открытые веса, Apache-2.0) через Ollama, по желанию. Без неё всё работает на правилах и шаблонах.
Почему так и почему эта модель — замер в [`docs/llm.md`](docs/llm.md).

| Функция | Что делает модель | Страховка |
|---|---|---|
| **Подбор по описанию своими словами** (`/podbor`, `POST /api/podbor/parse`, `app/services/intake.py`) | «Нужно 3 млн на закупку к сезону, отдам за полгода, есть грузовик в залог» → цель, сумма, срок, залог, поручитель; форма подбора заполняется, клиент видит «Поняли так: …» и правит. Сначала работают **правила** (мгновенно), модель зовётся, **только если они не уверены**: цель без ключевых слов, несколько сумм и ни одной «нужно», срок не найден | Модель заполняет только пробелы, ответ — строго по JSON-схеме, **числа — только из текста клиента**: сумму или срок, которых клиент не писал, придумать нельзя |
| **Черновик сообщения клиенту для аналитика** (карточка заявки → «Запросить данные» → «Сформулировать для клиента», `POST /api/bank/applications/{id}/client-message`, `app/services/client_message.py`) | Аналитик пишет коротко, для себя: «нужна ОСВ 62, выручка не бьётся с БКИ» → вежливый понятный текст для клиента. Аналитик читает, правит и отправляет сам | Черновик отбрасывается, если в нём **внутренняя кухня** (БКИ, скоринг, пороги, подозрения), **новые числа**, обещания или не русский текст — тогда шаблон для выбранного документа |

Общий клиент — `app/services/llm.py`: таймаут; после сбоя модель полминуты не вызывается, чтобы
запросы не ждали таймаут; любой сбой — правила или шаблон. Тексты причин отказа модель **не
пересказывает**: они написаны заранее и проверены, пересказ мог бы только исказить решение.

**Распознавание документов — без ИИ.** ОСВ по счёту 62 из 1С (XLSX/CSV) читается правилами
(`app/services/documents.py`): обороты по дебету сверяются с выручкой из заявки с НДС и без, аналитик
видит «сходится» или «расхождение N %». Таблица из 1С уже структурирована — правила здесь надёжнее модели.
Образцы для показа — `docs/samples/osv62_*.xlsx`.

### Как включить модель

Модель необязательна и включается одним флагом — всё остальное происходит само:

```bash
docker compose --profile llm up --build -d
```

1. Поднимается контейнер `ollama` (образ `ollama/ollama:0.40.11`).
2. Он сам скачивает модель `qwen3:4b-instruct-2507-q4_K_M` — точную сборку, на которой делали замер (первый раз ~2,5 ГБ, дальше
   берётся из тома `ollama`), и загружает её в память.
3. Приложение обращается к нему по адресу `http://ollama:11434` (так задано в `docker-compose.yml`).
   Пока модель скачивается, сайт работает на правилах и шаблонах — ничего не ломается.

Проверить, что модель готова:

```bash
docker compose logs -f ollama              # ход скачивания
docker compose exec ollama ollama ps       # модель в памяти — строка с qwen3:4b-instruct-2507-q4_K_M
```

Чтобы не писать флаг каждый раз, положите в `.env` строку `COMPOSE_PROFILES=llm` — тогда модель поднимается
обычным `docker compose up`. Выключить: убрать эту строку (или запускать без флага). Строка `LLM_URL=` с пустым
значением в `.env` отключает модель, даже если контейнер `ollama` запущен.

Как понять в интерфейсе, что ответила модель: на плашке «Поняли так» в подборе написано, что именно «уточнила
модель с открытыми весами» (например, «Цель, сумму уточнила модель…») (если фраза понятная, её разбирают правила без модели), под черновиком у аналитика —
«Черновик от модели с открытыми весами».

# Где API «налоговой» и БКИ

Моки — отдельные контейнеры `fns-mock` (порт 8101) и `bki-mock` (8102). Наружу они **не открыты**:
сайт ходит к ним внутри сети Docker. Посмотреть их ответы можно так:

- в кабинете банка: карточка любой заявки → блок «Проверки и источники»; сырой JSON — `GET /api/bank/applications/{id}` в Swagger;
- открыть моки наружу для демо: `docker compose -f docker-compose.yml -f docker-compose.mocks.yml up -d` —
  Swagger на `http://localhost:8101/docs` и `http://localhost:8102/docs`.

| Мок | Метод | Что отдаёт |
|---|---|---|
| ФНС | `GET /egrul/{inn}` | ЕГРЮЛ/ЕГРИП: название, ОГРН, дата регистрации, статус, ОКВЭД, руководитель, учредители |
| ФНС | `GET /transparent/{inn}` | «Прозрачный бизнес»: сотрудники, недоимка, уплаченные налоги, выручка и расходы |
| БКИ | `GET /report/{inn}?consent_id=…&purpose=…` | кредиты, остатки, платежи, просрочки за 24 мес.; без согласия — 403 |

Данные — в `mocks/data.py`: 10 компаний под сценарии, для любого другого ИНН с верной контрольной
суммой генерируется детерминированная синтетическая компания.

## Администратор: продукты, карта скоринга, журнал

«Продукты и скоринг» → **«+ Добавить продукт»** или **«Изменить»** у продукта: название, вид, цели, лимиты
суммы и срока, минимальный срок бизнеса, залог и поручитель, лимит без залога, базовая ставка, авто-лимит,
срок решения. Все поля проверяются (минимум не больше максимума, авто-лимит не больше суммы и т. д.).
Удаления нет — на продукт ссылаются заявки: снятая галочка «Продукт выдаётся» убирает его в архив, из
подбора и проверки шансов; черновик на нём не отправить. Каждая правка поднимает версию.
API: `POST /api/admin/products`, `PATCH /api/admin/products/{id}`.

Новая версия карты скоринга — `POST /api/admin/scoring-models`: перед включением пробный расчёт, сломанная
конфигурация не включится. Откат — кнопка «включить» у версии или `POST /api/admin/scoring-models/{v}/activate`.

Внизу страницы — **журнал изменений**: кто, когда и что поменял в продуктах, карте и тестовых данных.

## Тестовые данные: как поменять кредитную историю и сведения ФНС

Администратор банка (`admin@bank.local`) → вкладка **«Тестовые данные»**. Выбираете компанию и правите:

- **кредитную историю** — кредиты (кредитор, вид, остаток, платёж, погашение, действующая просрочка) и
  просрочки за 24 месяца (дней, сумма, сколько месяцев назад); есть готовые сценарии: «Чистая история»,
  «Небольшая просрочка больше года назад», «Просрочка 45 дней в этом году», «Просрочка больше 90 дней в
  прошлом», «Действующая просрочка»;
- **сведения ФНС** — статус в ЕГРЮЛ, дата регистрации, недоимка, выручка и расходы, сотрудники;
- **новую компанию** — «+ Новая компания»: название, ООО или ИП, ИНН (пусто — придумаем корректный),
  дата регистрации, руководитель, ОКВЭД, выручка и расходы. Она появится в ЕГРЮЛ, «Прозрачном бизнесе» и
  БКИ, а клиент подключит её по ИНН. Пока не подключена — её можно удалить.

Справа сразу видно, как это прочитает скоринг: уровень платёжной дисциплины и баллы, стоп-фактор,
запрет автоодобрения, долг и платежи.

**Где хранится.** Исходные данные — в `mocks/data.py`. Правки моки хранят у себя, в `bki.json` и
`fns.json` на томе `mockdata`, и накладывают поверх исходных; новые компании — в `companies.json`;
«Вернуть исходные» удаляет правку. Служебный API моков: `GET/PUT/DELETE /admin/reports/{inn}` (БКИ),
`GET/POST /admin/companies`, `GET/PUT/DELETE /admin/companies/{inn}`, `DELETE /admin/custom/{inn}` (ФНС).
Моки наружу не открыты; `docker-compose.mocks.yml` открывает их только на `127.0.0.1`.
Настоящие БКИ и ФНС банк, конечно, править не может — это пульт демо-стенда.

**Что меняется.** Новая заявка компании получит новый отчёт БКИ, «Проверка шансов» — новые сведения
ФНС, карточка компании — новый статус и дату регистрации. Уже рассмотренные заявки хранят ответ,
полученный при проверке (`external_checks`), — решение можно воспроизвести.

# Архитектура

**Модульный монолит на FastAPI + отдельный воркер конвейера.** Границы модулей
(`web`, `api`, `services`, `domain`) позволяют позже вынести конвейер и
интеграции в отдельные сервисы, а на хакатоне микросервисы добавили бы риск без
пользы для проверки.

```mermaid
flowchart LR
    B[Браузер<br/>Jinja2 + HTMX] --> APP[app<br/>FastAPI: web + API]
    APP --> DB[(PostgreSQL<br/>данные + outbox)]
    W[worker<br/>конвейер] -- "SKIP LOCKED" --> DB
    W --> FNS[fns-mock<br/>смоделировано]
    W --> BKI[bki-mock<br/>смоделировано]
    APP -. "разбор запроса,<br/>черновик сообщения" .-> LLM[ollama<br/>профиль llm]
```

- **Outbox вместо брокера.** Задача на обработку пишется в таблицу `jobs` в той же транзакции, что и переход `DRAFT → SUBMITTED`: если задача есть, заявка точно отправлена. Воркеров можно запустить несколько.
- **Машина состояний — единственное место смены статуса** (`app/domain`). Недопустимый переход отклоняет сервис, а не интерфейс. Каждый переход пишется в `status_history`: кто, когда, откуда, основание.
- **Скоринг ≠ решение.** Балльная карта даёт оценку риска, а кредитная логика с учётом продукта, суммы, срока и жёстких стопов решает: одобрить, отказать, предложить иные условия или отправить аналитику. Она же проверяет **покрытие платежей** (прибыль должна покрывать платежи по всем кредитам с запасом 25% — поэтому срок влияет на решение, а не только на ставку) и **сверяет выручку и прибыль из анкеты с отчётностью в ФНС**.
- **Откалиброванная карта.** Баллы — в шкале шансов (60 баллов ↔ вероятность дефолта 5%, +10 баллов — шансы дефолта вдвое ниже), веса получены логистической регрессией (`tools/calibrate.py`) на синтетическом портфеле из 200 тыс. заявок, пороги — из риск-аппетита. Просрочки учитываются по сроку и размеру (590-П, порог существенности). Залог работает через LGD по Базелю III: снижает ставку (ставка = база + PD × LGD) и поднимает лимит, но не баллы. Отчёт с допущениями и источниками — [`docs/calibration.md`](docs/calibration.md).

**Источники методики**

1. **Положение Банка России № 590-П**, п. 3.7 — сроки просрочки: до 5 дней — хорошее обслуживание долга, 6–30 — среднее, больше 30 — неудовлетворительное ([Гарант](https://base.garant.ru/71721612/5ac206a89ea76855804609cd950fcaf7/)).
2. **Базель III, CRE32** — потери при дефолте без залога 40% (CRE32.6), покрытой залогом части 20–25% и дисконт к стоимости залога 40% (CRE32.11) ([BIS](https://www.bis.org/committees/bcbs/basel-framework/81366/chapter.pdf)).
3. **EBA RTS 2016/06** — порог существенности просрочки: 500 евро и 1% долга; дефолт — после 90 дней ([EBA](https://www.eba.europa.eu/documents/10180/1597002/Final+draft+RTS+on+the+materiality+threshold+for+credit+obligations+%28EBA-RTS-2016-06%29.pdf/fe1db887-c6dc-4777-89c1-4f243584cafd)).
4. **Эксперт РА**, «Рынок кредитования МСБ по итогам 2025 года», 30.04.2026 — доля просрочки в портфеле МСБ снизилась с 4,4 до 4% ([raexpert.ru](https://raexpert.ru/researches/banks/msb_2025)).
5. **Исследование Точка Банка** (пересказ Mail.ru Финансов, 26.05.2026) — из компаний и ИП, зарегистрированных в 2022 году, к концу 2025-го работает половина ([Mail.ru Финансы](https://finance.mail.ru/article/v-rossii-iz-otkryityih-tri-goda-nazad-kompanij-zakryilas-kazhdaya-vtoraya-69210367/)).

Подробно, с диаграммами — в [`docs/architecture.md`](docs/architecture.md):
компоненты, конвейер заявки, диаграмма состояний, модель данных, скоринг и
решение, безопасность. Исследование и модель процесса — в [`docs/research.md`](docs/research.md).

# API

Всё, что делает сайт, доступно и через JSON API — для интеграций (мобильное приложение, 1С, партнёры)
и автотестов. В кабинете банка вкладка **«API ↗»** открывает Swagger: список операций, схемы и кнопку
«Try it out», чтобы вызвать метод прямо из браузера.

Документация — `/api/docs` (Swagger), спецификация — [`docs/openapi.json`](docs/openapi.json),
импортируется в Postman или Bruno как коллекция. Примеры запросов — [`docs/api.http`](docs/api.http).

- **Аутентификация:** `POST /api/auth/login` ставит cookie сессии.
- **Идемпотентность:** отправка заявки поддерживает заголовок `Idempotency-Key`.
- **Ошибки** в едином формате `{"error", "message", "details"}`.

# Настройки

Все параметры — переменные окружения. Для Docker скопируйте
[`.env.example`](.env.example) в `.env` и поменяйте значения. Без `.env`
используются демо-значения.

**Через `.env` для `docker compose`:**

| Переменная | По умолчанию | Что меняет |
|---|---|---|
| `SECRET_KEY` | случайный при старте | подпись cookie сессии. Не задан — генерируется при каждом старте (после перезапуска все выходят из кабинета). Для постоянного развёртывания задайте свой длинный секрет; публичные значения из примеров игнорируются |
| `POSTGRES_PASSWORD` | `kabinet` | пароль базы |
| `FNS_FAIL_RATE`, `BKI_FAIL_RATE` | `0` | доля случайных сбоев моков (0..1), чтобы показать надёжность |
| `PIPELINE_STEP_DELAY` | `0.8` | пауза между этапами конвейера, сек., чтобы в демо было видно движение статуса |
| `LLM_URL` | `http://ollama:11434` | адрес модели. Без профиля `llm` контейнера нет — сайт работает на правилах. Пустое значение — отключить модель совсем |
| `LLM_MODEL` | `qwen3:4b-instruct-2507-q4_K_M` | модель для подбора по описанию и черновиков сообщений |
| `COMPOSE_PROFILES` | пусто | `llm` — поднимать Ollama без флага `--profile` |

**Остальные параметры приложения** ([`app/config.py`](app/config.py)). Адреса базы,
моков и папки загрузок `docker-compose.yml` задаёт сам:

| Переменная | По умолчанию | Что меняет |
|---|---|---|

# Разработка без Docker

```bash
python3.12 -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt

# PostgreSQL должен быть запущен
export DATABASE_URL=postgresql+psycopg://kabinet:kabinet@localhost:5432/kabinet

uvicorn mocks.fns:app --port 8101 &
uvicorn mocks.bki:app --port 8102 &
alembic upgrade head
python -m app.seed
RUN_WORKER_IN_APP=true uvicorn app.main:app --reload --port 8000
```

`RUN_WORKER_IN_APP=true` запускает воркер внутри веб-процесса. В Docker воркер — отдельный контейнер.

# Структура

**Python 3.12 · FastAPI · PostgreSQL 16 · SQLAlchemy 2 + Alembic · Jinja2 + HTMX · Docker Compose.**
LLM с открытыми весами (Qwen3-4B-Instruct-2507 через Ollama) — по желанию.

```
app/
  domain/        машина состояний и сервис переходов (единственное место смены статуса)
  services/      заявки, согласия, валидация, интеграции, скоринг (карта — scorecard.json),
                 кредитная логика, объяснения, аналитик, конвейер, продукты, тестовые данные
  api/           JSON API + схемы (OpenAPI)
  web/           HTML-кабинеты клиента и банка, пульт тестовых данных
  templates/     Jinja2-шаблоны по макетам
  static/        CSS из дизайн-токенов макетов, htmx, шрифт Onest
  worker.py      воркер конвейера (outbox, SKIP LOCKED, истечение сроков)
  seed.py        демо-данные
mocks/           моки ФНС и БКИ (отдельные контейнеры), синтетические компании, служебный API правок

tests/           pytest

  readme/        скриншоты и GIF этой страницы
```

# Потенциал развития

- **Реальные интеграции** вместо моков: контракт клиентов в `app/services/integrations.py` уже отделён.
- **Методика:** перекалибровка карты на истории дефолтов банка (`python tools/calibrate.py --data history.csv`,
  новая версия — через `POST /api/admin/scoring-models`) и ежегодная проверка Gini и PD по диапазонам; запрос в
  БКИ по поручителю (согласие уже собираем); оценка залога оценщиком банка вместо слов клиента; сверка выручки
  с оборотами по счёту (выписка, 1С, открытые API банков); для овердрафта — лимит от среднемесячных поступлений.
- **Отдельные сервисы** для конвейера и интеграций по границам модулей, брокер поверх outbox.
- **Документооборот** и реальная ЭП, подтверждение полномочий при подключении компании, уведомления.
- **Вход и регистрация:** Госуслуги или ЭП и подтверждение телефона вместо пароля, восстановление доступа,
  приглашение коллег одноразовой ссылкой, удаление аккаунта по запросу (152-ФЗ).
- **Безопасность:** шифрование чувствительных полей, общий счётчик попыток входа (Redis) для нескольких копий
  приложения, SSO для сотрудников банка, токены для внешних клиентов API.
